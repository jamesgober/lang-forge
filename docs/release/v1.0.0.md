# lang-forge v1.0.0 — The LexerSketch Contract

**The API freeze.** v1.0.0 makes the 0.2.0 surface, the `.lsf` schematic
format, and the parser's guarantees a stable contract: no breaking change
before 2.0. The code is the same as 0.2.0, which reached this point through an
adversarial review whose findings were all fixed before that release. What
1.0 adds is the promise — what exactly is frozen, what may grow, and what was
never promised — recorded in `docs/API.md#stability`.

## What is lang-forge?

LexerSketch: describe a language in a short `.lsf` schematic — its tokens, its
grammar, its operators and their precedence, the capabilities it includes —
and `Language::from_lsf` forges a working front end for it. The forged language
lexes and parses source text into the family's lossless `syntax-lang` tree,
reports every problem as a `diag-lang` diagnostic, never fails and never
panics, and wires the schematic's capabilities into a `pass-lang` pipeline. It
is the capstone (LGEN tier) of the `-lang` language-construction family.

## What 1.0 promises

### The surface

Five names, frozen with their trait implementations:

- `Language` — `from_lsf`, `name`, `version`, `extensions`, `capabilities`,
  `kind`, `kind_name`, `lex`, `parse`, `pipeline`; `Clone`, `Debug`, `Send`,
  `Sync`, `FromStr`.
- `Parse` — `tree`, `source`, `language`, `diagnostics`, `has_errors`,
  `report`, `into_tree`, `dump`.
- `Kind` — `Copy`, `Eq`, `Ord`, `Hash`, `Debug`, `syntax_lang::TokenKind`.
- `Capability` — a boxed `pass_lang::Pass` over a `Parse`.
- `Error` — `diagnostics`, `Display`, `core::error::Error`.

`syntax_lang`, `diag_lang`, and `pass_lang` stay re-exported. New methods and
types arrive in minor releases.

### The schematic format

Every table, key, value form, and default keeps its meaning, as do the rule
language and expression rules. New keys and rule forms may be added in a minor
release. A schematic that forges under one `1.x` release forges under every
later one — the single exception being a schematic later found to hang or crash
the parser, which may be refused as a bug fix.

### The trees for valid input

For input that parses without an error, the tree is fixed by the schematic:
which nodes exist, their kinds and names, and where whitespace and comments
sit. Kind naming — rule names, literal texts, the built-in names, and the
default operator node names `binary`, `prefix`, and `postfix` — does not
change.

### The guarantees

Parsing never fails and never panics. Every tree covers every byte of its
source. Recursion is bounded at 768 grammar levels — at most about 256 KiB of
stack in a release build — so no input can exhaust the stack; the limit may be
raised in a minor release, never lowered. Forging never panics. `Parse::dump`
keeps its format, so snapshot tests written against it keep passing.

### What is not promised

The wording of diagnostics; for input with errors, the exact shape of the
recovered tree and which errors are reported, since recovery may improve; the
`Debug` output of any type; and performance figures, which are tracked but are
measurements, not guarantees.

## Breaking changes

**None.** The 0.2.0 surface is unchanged.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu, from a sibling-free copy, as CI
checks the crate out), Rust stable and the 1.85 MSRV; macOS runs through the
configured CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
cargo test
cargo test --all-features
cargo test --no-default-features
cargo build --examples
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 test --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo +1.85 clippy --all-targets --no-default-features -- -D warnings
cargo deny check
cargo audit
cargo publish --dry-run
cargo bench --bench bench
```

All green. Counts at this tag (identical for every feature combination):

- 71 unit + 39 integration (forging) + 20 integration (parsing) + 5 property +
  13 regression + 64 doctests. The doctests include every `rust` example in
  `README.md` and `docs/API.md`.

Benchmark baselines are unchanged from 0.2.0 (x86_64, release profile; parse
figures include lexing, building, and dropping the tree):

| Benchmark | Windows | Linux (WSL2) |
|---|---:|---:|
| `forge/mini` | ~38 µs | ~23 µs |
| `lex/mini/1MB` | ~3.7 ms | ~1.8 ms |
| `parse/mini/1MB` | ~57 ms | ~24 ms |
| `parse/json/1MB` | ~60 ms | ~34 ms |
| `parse/speculative/256KB` | ~33 ms | ~13 ms |

## What's next

Additive `1.x` work, none of it changing the frozen surface: emitting a
tree-sitter grammar for a forged language through `treesitter-lang`, named
token classes beyond the built-ins (such as `CHAR`), custom token patterns,
contextual keywords, and a reusable parse session that keeps its buffers
between parses.
