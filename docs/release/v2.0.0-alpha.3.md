# lang-forge v2.0.0-alpha.3: Lexer and Forge Limits

**A fix release for 2.0.0-alpha.2.** The format-2 lexer could take time
quadratic in its input, and forging could take a very long time on a short
sketch. Any editor, language server, or service that lexes untrusted text, or
forges sketches it did not write, could be stalled. In this release lexing is
linear in the input, and compiling a sketch's token regexes is held to a
budget of work as well as memory.

Two smaller fixes come with it: loading a forged language image no longer
reserves far more memory than the image, and `Parse::dump` no longer grows
with the square of the tree's depth.

## What is lang-forge?

Describe a language in a short `.lsf` sketch, with its tokens, its grammar,
its operators and their precedence, and the capabilities it includes, and
`Language::from_lsf` forges a working front end for it. The forged language
lexes and parses source text into the family's lossless `syntax-lang` tree,
reports every problem as a `diag-lang` diagnostic, never fails and never
panics, and wires the sketch's capabilities into a `pass-lang` pipeline.

## What was wrong

**Lexing.** A format-2 token class with a regex is a candidate at every
position where it can start. The scanner ran the class's automaton to its
longest match, which means reading until the automaton can go no further.
That point can lie far past the token the scanner then takes. With these two
classes:

```toml
[lexer.tokens]
T = { regex = '-*b' }
U = { literal = "-" }
```

a run of dashes with no `b` makes `T` read to the end of the run from every
dash, while `U` takes one dash at a time. 80,000 dashes took 6 seconds, and
1 MB would have taken about a quarter of an hour. The same happened with a
regex whose match a condition refuses (`not_followed_by`), with the regex
parts of string openers, and with embedded string tokens.

**Forging.** The regex compiler capped the size of each automaton, its table,
and its construction keys, which bounds memory. It did not bound work. A
pattern of many distinct optional classes, `a[^c1]?[^c2]?...[^c1000]?` (7 KB),
forged in 35 seconds, and with 4,000 classes it ran for minutes. A 17-byte
nested repetition, `((x?){1000}){400}`, took about a second to be refused.

## What's new

### Lexing is linear in the input

The scanner now keeps a memo for each lex. For each regex it remembers the
`(position, state)` pairs its runs passed and the furthest accepting end a
run from each pair reaches. A later run that arrives at a remembered pair
knows the rest of its answer and stops there, so no run reads the same text
in the same state twice, and the total work is linear in the input for a
given sketch. This is the method of Reps, "Maximal-munch tokenization in
linear time" (1998).

The memo costs nothing on ordinary input. A run reads its first 32 bytes
without it, and only a run that reads further is remembered, lazily: its
pairs are worked out, by running it once more, only when a later long run
starts well before the end of what it read. Ordinary tokens never get there.

| Input | alpha.2 | alpha.3 |
|---|---|---|
| 10,000 dashes | 80 ms | 1.6 ms |
| 80,000 dashes | 5.7 s | 14 ms |
| Mox corpus, 1 MB | 21.1 to 22.9 ms | 19.9 to 22.2 ms |

(Release build on Windows, a loaded machine. The Mox row is the best of 40
runs, repeated six times for each version. The dash rows use the sketch
above.)

### Forging has a time budget

Compiling the token regexes of one sketch may now take 8,388,608 steps in all.
A step is one alphabet boundary looked at, one NFA state built, or one unit of
determinization: a state visited in a closure, a transition put in a bucket,
a character class examined. The count is checked inside the loops, so a
pattern that would run on stops at once. A regex that goes past the budget is
refused with `LSF3201`:

```text
regex `((x?){100}){100}` takes too long to compile: the token regexes of a sketch may take 8388608 steps together
```

The Mox sketch takes about 21,000 steps, so the budget leaves a wide margin.
Two caps also come down: one regex may tell at most 256 sets of characters
apart (4,096 before), and its NFA may have at most 262,144 states (1,048,576
before). The patterns above are now refused in 3 to 40 ms.

### Smaller fixes

- **Images.** A count of elements in a language image was checked against
  each element's smallest encoding, one byte, and then reserved at the
  element's size in memory, up to 32 bytes. A forged 16 MiB image reserved
  512 MiB before it was refused. The reservation is now limited to what the
  bytes left could hold.
- **`Parse::dump`.** Every level of the tree was indented two spaces, so a
  16 KB operator chain dumped 193 MB. Indentation now stops at 64 levels, and
  a deeper line starts with its depth in brackets, such as `[65] `. Trees up
  to 64 levels deep dump exactly as before.

## Breaking changes

- A sketch whose regexes forged in alpha.2 but go past the new budget or caps
  is refused with `LSF3201`. None of the example sketches or the Mox sketch
  comes close.
- `Parse::dump` on trees deeper than 64 levels prints differently.

## Not in this release

An operator chain builds a tree as deep as the chain, and the derived
`Clone`, `PartialEq`, and `Debug` of `syntax_lang::Node` recurse, so cloning a
tree for `"1+".repeat(200_000)` overflows the stack. The fix belongs in
`syntax-lang`, with iterative versions of those traits on `Node`.

## Upgrading

```toml
[dependencies]
lang-forge = "2.0.0-alpha.3"
```

The `.lsf` format, the trees for input within the limits, and the image
format are unchanged.
