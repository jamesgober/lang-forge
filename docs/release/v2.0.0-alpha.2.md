# lang-forge v2.0.0-alpha.2 — Parser Limits in Linear Time

**A security fix for 2.0.0-alpha.1.** Past the parser's depth limit, parsing
time grew exponentially with every level of nesting. Mox source with fifty
nested array literals parsed in about 80 ms in LexerSketch; at sixty it did
not finish, and sixty-five nested `list(` calls took 77 seconds. Any editor,
language server, or service that parses untrusted text with a forged language
could be stalled by one short line. In this release the depth limit stops the
parse at once, with one located diagnostic, and every parse is held to a step
budget proportional to its input. Hostile grammars and inputs now end with an
error instead of running on.

Nothing else changes. The `.lsf` format, the trees for input within the
limits, and the image format are the same as alpha.1. The LSF2 work alpha.1
scheduled for alpha.2 moves to alpha.3.

## What is lang-forge?

LexerSketch: describe a language in a short `.lsf` sketch, with its tokens,
its grammar, its operators and their precedence, and the capabilities it
includes, and `Language::from_lsf` forges a working front end for it. The
forged language lexes and parses source text into the family's lossless
`syntax-lang` tree, reports every problem as a `diag-lang` diagnostic, never
fails and never panics, and wires the sketch's capabilities into a
`pass-lang` pipeline.

## What was wrong

The parser counts every recursive step against a limit of 768 grammar levels,
which bounds its stack. In alpha.1, reaching the limit inside a speculative
attempt *failed* that attempt and marked its result as unfit for the memo,
which only knows results that depend on the rule and the position alone. A
failed attempt is retried: the next alternative, the item after a predicate
that failed, the operand after a lookahead that failed. Mox's array entries
begin with the predicate `&(expr '=>')`, which parses a whole expression to
see whether a key follows. So at every level past the limit, both the
predicate and the entry went down the same too-deep path again, and none of
it could be remembered. Instrumented, one more level of nesting past the
first trip took the parse from 31,000 steps and 16 trips of the limit to 7.8
million steps and 327,600 trips. The level after that did not finish.

A second path had the same shape. The progress guard cuts a cycle of rules
that consumes nothing, which can happen where the end of the input stands for
a line break. When it fired, every result around it was kept out of the memo,
so a grammar whose statement list recurses through `NEWLINE` took exponential
time on unclosed blocks before the end of input: 2.6 s at 22 levels.

## What's new

### Limits stop the parse

```rust
use lang_forge::Language;

let lang = Language::from_lsf(
    "[language]\nname = \"p\"\n[rules]\nvalue = \"NUMBER | '(' value ')'\"\n",
)?;
let source = format!("{}1{}", "(".repeat(10_000), ")".repeat(10_000));
let parse = lang.parse(&source);

// One diagnostic, where the limit was reached, after about a thousand steps.
assert_eq!(parse.diagnostics().len(), 1);
assert!(parse.diagnostics()[0].message().contains("nested too deeply"));
assert!(parse.steps() < 2_000);
// Still lossless: the tokens not parsed are kept in an `ERROR` node.
assert_eq!(parse.tree().text(&source), Some(source.as_str()));
# Ok::<(), lang_forge::Error>(())
```

The depth limit is now a hard stop of the whole parse, whether the parser is
committed or only trying an alternative. Every place that would retry checks
for the stop and unwinds instead. The attempt in progress is rewound. The
tree keeps what the parse had committed to, the tokens not yet parsed go into
one `ERROR` node inside the innermost open node, and every open node is
closed. One diagnostic, `LF1003`, points at the token where the limit was
reached. Nothing after the stop is parsed or reported.

Why a stop and not a smarter failure: a failure is the wrong answer as well
as the slow one. An alternative that reached the limit might have matched;
choosing the next one would be a guess. A depth-limited result can never
enter the memo, so it can never poison it.

### A step budget

```rust
use lang_forge::{Language, ParseBudget};

let lang = Language::from_lsf("[language]\nname = \"n\"\n[rules]\nfile = \"item*\"\nitem = \"NUMBER\"\n")?
    .with_parse_budget(ParseBudget::new(100, 0)); // an absolute cap

let source = "1 ".repeat(500);
let parse = lang.parse(&source);
assert_eq!(parse.diagnostics()[0].code().map(|c| c.to_string()).as_deref(), Some("LF9002"));
assert_eq!(parse.steps(), 100);
assert_eq!(parse.tree().text(&source), Some(source.as_str()));
# Ok::<(), lang_forge::Error>(())
```

- `ParseBudget`: `base + per_token × significant tokens` steps.
  `ParseBudget::DEFAULT` is 1,048,576 plus 4,096 per token; `new(u64::MAX, 0)`
  turns the budget off, and `per_token` zero makes it absolute.
- `Language::with_parse_budget` and `Language::parse_budget`. The budget is a
  setting of the `Language` value: it covers `parse`, `parse_file`, and each
  self-injection, and is not stored in images.
- `Parse::steps`: the work a parse took, in the budget's steps.
- `LF9002`: a parse that used up its budget stops the same way the depth
  limit stops it.

A step is a grammar level entered, a token matched, or an operator. An
alternative examined, a memo entry looked at, or an event copied from a
remembered attempt is an eighth of a step. Every loop the parser runs per step
is counted, so the budget bounds the parser's time whatever the grammar.

Ordinary input takes 3 to 15 steps per token on the example languages and the
Mox corpus. The most the Mox sketch takes is about 2,000 per token, on wide
array literals nested just under the depth limit. The default is reached only
by what it exists for:

- grammars whose cost per token grows with the grammar, such as a cycle the
  progress guard cuts at the end of the input, exponential in the number of
  rules in it;
- input that makes speculation scan far ahead from every token, which is
  quadratic. An alternative such as `IDENT* ';'`, tried before a shorter one
  that matches, rescans the rest of the input at every token: 100,000
  identifiers took 18 s in alpha.1 and now stop in about 1.7 s.

A tool that runs sketches it did not write, such as LexerSketch Studio's
preview (`_lexersketch/ISSUES.md` P46), can set a tighter or absolute budget.

### The audit

Every path the memo cannot cover was checked:

- **The depth limit**: now a stop (above).
- **The progress guard**: a result is now remembered unless the cycle the
  guard cut ran through a rule invocation outside it. A result whose cycle was
  at its own position is replayed only where no rule is active at that
  position yet. A property test fails without that second rule. Within one
  position the guard can still cost time exponential in the number of rules in
  a cycle: a property of the grammar, not the input, and the budget bounds it.
- **P09 follow-up**: how deep a remembered attempt went now includes the
  attempts it replayed. Before, an attempt holding replays could be replayed
  where parsing it again would reach the limit. A unit test fails without the
  fix.
- **Work no step counted**: tokens matched in a strict attempt (the fast
  path), operators in a postfix chain, a choice's alternatives, memo chain
  walks, the predicate guard's walk, and replayed events are all counted now.
- **Grammar-sized loops**: a contextual keyword operator no longer scans
  every rule of the grammar for the rule that owns it. Error messages are
  built only when reported (at most one per token), and an expected set is
  described from at most seven of its members.

## Breaking changes

- Input that reaches the depth limit stops the parse, in both formats. 1.x
  and alpha.1 reported the limit and parsed on, and alpha.1 hung on some such
  input. Because an attempt can go a level or two deeper per nesting level
  than the parse it guards, slightly less nesting fits: in the Mox sketch,
  array literals stop at 54 levels and `list(` calls at 63, where alpha.1
  accepted 55 and 64 and then stalled. A too-deep input now gets one
  diagnostic instead of a cascade.
- Every parse has a step budget: input that costs more than 4,096 steps a
  token, plus a base of about a million, stops with `LF9002`.

## Measurements

The fix, single runs, release build, Windows x86_64 (test copy of the Mox
sketch):

| Input | 2.0.0-alpha.1 | 2.0.0-alpha.2 |
|---|---:|---:|
| Mox array literals, 50 deep | 1.2 ms | 1.2 ms (75,934 steps) |
| Mox array literals, 55 deep | 118 ms | stops: 40–50 µs (1,096 steps) |
| Mox array literals, 56 deep | did not finish in 30 s | stops: 25 µs (1,096 steps) |
| Mox array literals, 10,000 deep | did not finish | stops: 1.2 ms (1,096 steps) |
| Mox `list(` calls, 64 / 65 deep | 28 ms / 77 s | stops: 50–90 µs / 30 µs (1,179 steps) |
| Unclosed blocks before the end of input, `NEWLINE`-recursive grammar, 22 deep | 2.6 s | 57 µs (1,031 steps) |
| The same, 10,000 deep | did not finish | stops: 0.6 ms (879 steps) |
| `IDENT* ';' \| IDENT` over 100,000 identifiers | 18 s | budget stop: 1.75 s (410 million steps) |

20,000 tokens; the parser stops after about a thousand steps.

nested 50 deep, where each level's entry predicate rescans the levels below.

## Verification

Run on Windows x86_64 with stable (1.95), 1.99, and the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings              # also +1.85, +1.99
cargo clippy --all-targets --no-default-features -- -D warnings       # also +1.85, +1.99
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
```

All green. Counts (identical for every feature combination): 123 unit
(including 8 parser properties, 2 of them new) + 10 limits (1 property, new)
+ 42 forging + 20 parsing + 7 properties + 21 regressions + 3 memory + 28
format-2 lexer + 23 format-2 grammar + 9 Mox + 7 multi-file sketch + 5 image +
7 format-2 regressions + 133 doctests. Every test from alpha.1 passes
unchanged. The parser properties were also soaked at 20,000 cases each.
